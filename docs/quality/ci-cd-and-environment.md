# Dev static Hosting and CI/CD

## Scope and routing

The Dev release is a Next.js static export hosted by the existing classic Firebase Hosting site `rental-2c497`, whose site ID matches its project ID and whose custom domain is `dev.arentzo.com` (confirmed by the separate Hosting inspection). The workflow deploys only on pushes to `dev`; pull requests targeting `dev` run verification but never deploy. This workflow has no `main` or `prod` trigger and does not deploy App Hosting, Cloud Run, or Functions.

`next.config.mjs` uses `output: 'export'`, `trailingSlash: true`, and unoptimized remote images. Firebase serves only `out/`, with an explicit `.firebaserc` target mapping `dev` to site ID `rental-2c497`. The workflow also checks the target list through Firebase CLI before deploy and runs a post-release HTTP smoke test against `https://dev.arentzo.com`.

Static export required route-specific changes. `/product/[id]` and `/my-rentals/[id]` are now static query routes (`/product/?id=…` and `/my-rentals/?id=…`) because arbitrary listing and booking IDs cannot be enumerated at build time. Internal product and rental links use the query routes. Existing deep links remain usable through two standalone compatibility HTML files in `public/`, with exact one-segment Hosting rewrites for `/product/:id` and `/my-rentals/:id`. Their shared external script validates the decoded ID, redirects only to a fixed same-origin query route, preserves the source query/hash except an incoming `id` or `next`, and rejects malformed IDs. These files are independent of Next routes so arbitrary IDs need not be generated at build time. `/home` is a Hosting redirect to `/`; the blog route uses its explicit `BLOG_SLUGS` list and disables unknown generated params. Login/signup now read `next` in client components under Suspense. `robots.txt` and `sitemap.xml` are marked static. Product and rental-detail metadata is generic because query values are not available to static server rendering.

No Next Route Handlers, Server Actions, `cookies()`, `headers()`, or Proxy are present in the inspected app. The Supabase adapter creates `@supabase/supabase-js` in the browser with PKCE and persistent client storage; it does not use `@supabase/ssr` or server cookies. Static hosting therefore does not need to write auth cookies. Sessions remain in browser storage; route guards are client-side and database authorization must continue to rely on Supabase RLS. Supabase SSR cookie refresh is not available in this frontend-only deployment. Firebase Hosting passes cookies through only to its Functions/Cloud Run backends (and only `__session`), which this setup does not use.

## Automated Dev push flow

`.github/workflows/ci.yml` is the single Dev pipeline. On a `dev` push it validates the project config and anon key, runs lint and deterministic unit tests, builds `out/` using the verified Rental Dev public config, serves the export in a demo Firebase Hosting emulator for Playwright responsive and static-query route checks, and uploads that exact static artifact. Immediately before upload, strict validation allows exactly the two required hidden `.well-known` assets, rejects sensitive paths/content, verifies their JSON bodies, writes and checks the full `GITHUB_SHA` provenance, and records a sorted content-tree SHA-256. The upload action explicitly includes hidden files only after this allowlist validation. After download, a second verifier checks the expected artifact SHA from the verify job, tree shape, allowlist, complete association bodies, and exact commit provenance before Firebase deploy. Firebase serves both marker files with `Cache-Control: no-store`. The post-deploy verifier uses bounded retries and requires the live provenance to equal that run's `GITHUB_SHA`, the artifact SHA to match, and both live `.well-known` JSON bodies to exactly equal their checked-in sources; an older release fails the job. A dependent deploy job deploys only `hosting:dev` to project `rental-2c497`. No static mock or substitute catalog is generated; product data and user features remain client-side Supabase calls. The browser suite uses synthetic fixtures for deterministic layout and retry checks; it is not signed-in account E2E.

Pull requests into `dev` use inert Supabase placeholders, run lint/unit/static build and local Hosting emulator browser checks, and do not upload or deploy a Dev release. The `dev` push job overrides the checked-in `.env*` values with Actions Variables and verifies the built bundle contains only the Rental Dev Supabase host and no CI placeholder. The workflow never reads a service-role key.

`vercel.json` is at the repository root, where the Vercel Git project previously built this Next.js app. Its `git.deploymentEnabled` map disables only the `dev` branch and the review branch `feat/dev-static-hosting-review`, preventing Firebase-Dev-configured source from producing Vercel preview/branch deployments. It does not change `main`, `prod`, or any other branch; Vercel leaves unspecified branches at their default. The review branch includes this guard in its first pushed commit. This does not disable or redirect Firebase Hosting: `dev` pull requests run verification only, and the Firebase live deploy remains limited to a `dev` push after merge.

## GitHub configuration required before a Dev push can deploy

Add these as GitHub Actions **repository Variables** for the build. They are public client configuration and are embedded in the browser bundle by design:

| Variable | Value/source |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | `https://astiltnwyoxtcisedcyx.supabase.co` (Rental Dev) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | The active Rental Dev legacy anon JWT from Supabase API Keys; the workflow verifies JWT role `anon` and ref `astiltnwyoxtcisedcyx`. The client also accepts `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` with the modern `sb_publishable_` format; if used, CI verifies that the configured project accepts it. Never use a service-role or secret key. |

`NEXT_PUBLIC_SITE_URL` must be a GitHub Actions repository Variable set to exactly `https://dev.arentzo.com`; on `dev` pushes, the workflow reads this variable and fails closed unless it exactly matches. The build and auth callback use this origin. It must not be copied from a Preview or Production domain.

Rental Dev Supabase Auth must allow the web callback `https://dev.arentzo.com/auth/callback` for sign-up and password-reset links. This pass only inspected the client callback path; it did not read or modify Supabase Auth URL settings.

In GitHub **Settings → Environments → dev → Variables**, add `GCP_WORKLOAD_IDENTITY_PROVIDER` and `GCP_SERVICE_ACCOUNT` only after the corresponding Google Cloud WIF trust has been provisioned. These are resource identifiers, not credentials. The workflow requests the short-lived GitHub OIDC token only in the `deploy-dev` job. No Firebase token, service-account JSON key, or other long-lived secret is used.

## Google Cloud trust and remaining access gate

The intended auth path is Google Workload Identity Federation through a dedicated service account. Use issuer `https://token.actions.githubusercontent.com` and map `google.subject=assertion.sub`, `attribute.repository_id=assertion.repository_id`, `attribute.ref=assertion.ref`, and `attribute.workflow_ref=assertion.workflow_ref`. The provider condition should require `assertion.repository_id == '1127331378'`, `assertion.ref == 'refs/heads/dev'`, `assertion.event_name == 'push'`, and `assertion.workflow_ref == 'VeloriaTechPvtLtd/arentzo-web/.github/workflows/ci.yml@refs/heads/dev'`. Bind `roles/iam.workloadIdentityUser` to the service account using the immutable repository ID principal set, only after the provider condition is enforced. Required GitHub Environment `dev` Variables are the full provider resource name and service-account email; they are identifiers, not secrets. No provider, service account, or IAM binding is currently verified or configured.

Firebase documents that custom roles cannot currently control Hosting access. Firebase Hosting Admin (`roles/firebasehosting.admin`) is broad: it includes Hosting site create/delete/get/list/update; Firebase CLI deployment also requires API Keys Viewer (`roles/serviceusage.apiKeysViewer`). This is broader than release upload. No IAM trust, service account, credential, or role has been created or changed in this patch. A project owner must provision and review this trust/role combination before enabling deployment; the deployment job will fail closed if its two environment Variables are missing.

The separate worker confirmed a current live Hosting release and connected `dev.arentzo.com`, but this local workflow has not been run with the verified Actions Variables or WIF identity. Local export/browser checks used isolated fixtures; the actual Rental Dev anon key was not included in the checked-in prototype. The GitHub Actions Variables write path returned 403 and no variables were added. No Dev release is claimed until a real `dev` push passes and the workflow smoke test confirms the public site.

## Verification references

- [Next.js static exports](https://nextjs.org/docs/app/guides/static-exports) documents unsupported dynamic params without `generateStaticParams`, cookies, redirects, rewrites, Proxy, and default image optimization.
- [Firebase Hosting configuration](https://firebase.google.com/docs/hosting/full-config) documents static file routing, redirects, explicit hosting targets, and Functions/Run rewrites.
- [Firebase Hosting cache and cookie behavior](https://firebase.google.com/docs/hosting/manage-cache) documents that backend requests strip cookies except `__session`.
- [Firebase IAM permissions](https://firebase.google.com/docs/projects/iam/permissions) lists Hosting roles and says custom roles are not currently supported for Hosting.
- [Google GitHub Actions auth](https://github.com/google-github-actions/auth) documents OIDC Workload Identity Federation; [Firebase CLI auth](https://github.com/firebase/firebase-tools#authentication) documents Application Default Credentials.
- [Supabase SSR auth guidance](https://supabase.com/docs/guides/auth/server-side/advanced-guide) distinguishes browser local storage from cookie storage required for SSR.
